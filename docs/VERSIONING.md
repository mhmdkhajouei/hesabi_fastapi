# خط‌مشی نسخه‌گذاری و تکامل API

## ۱. مرور کلی و اهداف

این سند قرارداد رسمی نسخه‌گذاری API و استراتژی مدیریت چرخه حیات سرویس **Hesabi API** را مشخص می‌کند. هدف بنیادین این سیاست، تضمین پایداری، پیش‌بینی‌پذیری قراردادها برای مصرف‌کنندگان (فرانت‌اند، موبایل و کلاینت‌ها) و جلوگیری از اختلال در برنامه‌ها هم‌زمان با توسعه مداوم پلتفرم است.

تمامی قوانین و تعهدات این سند برای کلیه اندپوینت‌های ارائه‌شده در سیستم لازم‌الاجرا است.

---

## ۲. معماری نسخه‌گذاری

سرویس Hesabi API از الگوی **نسخه‌گذاری در مسیر آدرس (URI Path Major Versioning)** به عنوان قرارداد اصلی استفاده می‌کند:

* ساختار آدرس‌های پایه: `/api/v{MAJOR}/...` (مانند `/api/v1/categories/` و `/api/v1/transactions/`).


* انتشارهای داخلی سیستم از نسخه‌گذاری معنایی (`MAJOR.MINOR.PATCH`) پیروی می‌کنند، اما در رابط عمومی وب تنها شماره نسخه اصلی (`MAJOR`) نمایش داده می‌شود.


* تمامی قابلیت‌های جدید، بهینه‌سازی‌ها و تغییرات سازگار بدون تغییر در پیشوند آدرس، به صورت درجا (In-Place) روی نسخه فعال فعلی (`v1`) اعمال می‌شوند.



---

## ۳. قرارداد سازگاری رو به عقب (Backwards Compatibility Contract)

### ۳.۱ تغییرات غیرشکننده (مجاز درون نسخه جاری)

تغییرات زیر به عنوان تغییرات سازگار شناخته شده و پیاده‌سازی آن‌ها درون نسخه اصلی فعال (`v1`) بدون نیاز به منسوخ‌سازی یا ارتقای نسخه مجاز است:

* افزودن اندپوینت‌های جدید به سیستم.


* اضافه کردن فیلدهای اختیاری (Optional) یا پارامترهای کوئری جدید به درخواست‌ها.


* اضافه کردن کلیدها و فیلدهای جدید به ساختار پاسخ‌های خروجی JSON.


* تغییر ترتیب کلیدها در آبجکت‌های خروجی.


* آسان‌تر کردن اعتبارسنجی ورودی‌ها (مانند افزایش سقف مجاز کاراکترها).

### ۳.۲ تغییرات شکننده (نیازمند انتشار نسخه اصلی جدید)

اقدامات زیر باعث شکستن کدهای سمت کلاینت می‌شوند و اعمال آن‌ها اکیداً مستلزم راه‌اندازی یک نسخه اصلی جدید (مانند `/api/v2/`) است:

* حذف، تغییر نام، یا تغییر مسیر اندپوینت‌های موجود.


* حذف، تغییر نام، یا تغییر نوع داده (Type) فیلدهای موجود در اسکیماهای خروجی.


* اجباری کردن فیلدهای اختیاری در بدنه درخواست‌ها.


* سخت‌گیرانه‌تر کردن قوانین اعتبارسنجی ورودی‌ها.


* تغییر در پروتکل احراز هویت یا سطوح دسترسی اندپوینت‌ها.

## ۴. چرخه حیات منسوخ‌سازی و بازنشستگی (RFC 8594 و RFC 9745)

سیاست منسوخ‌سازی و از رده خارج کردن اندپوینت‌ها در Hesabi API بر پایه استانداردهای RFC 8594 و دستورالعمل AIP-185 گوگل تنظیم شده است.

### ۴.۱ بازه مهلت و زمان‌بندی اعلام

* **بازه استاندارد:** هر اندپوینت یا اسکیمایی که منسوخ اعلام شود، دست‌کم به مدت **۶ ماه (۱۸۰ روز)** کاملاً فعال باقی می‌ماند تا مصرف‌کنندگان زمان کافی برای تطبیق و مهاجرت داشته باشند.


* **بازه اضطراری امنیتی:** در صورت شناسایی رخنه یا آسیب‌پذیری بحرانی امنیتی، بازه بازنشستگی به یک مهلت ۳۰ روزه تسریع می‌یابد.



### ۴.۲ هدرهای ماشین‌خوان HTTP

در طول دوره ۶ ماهه منسوخ‌سازی، اندپوینت مربوطه همچنان پاسخ موفقیت‌آمیز (`200 OK`) تولید می‌کند، اما هدرهای زیر توسط دیپندنسی `DeprecateRoute` به پاسخ تزریق می‌شوند:

* **`Deprecation`**: با مقدار `"true"` برای اعلام رسمی منسوخ شدن اندپوینت.


* **`Sunset`**: حاوی تاریخ و زمان دقیق توقف کامل سرویس با فرمت RFC 7231 (مثلاً `Thu, 31 Dec 2026 00:00:00 GMT`).


* **`Link`**: پیونددهنده به آدرس جایگزین با متادیتای `rel="successor-version"` جهت راهنمایی کلاینت به نسخه مدرن.



### ۴.۳ مستندسازی و OpenAPI

* برای تمامی متدهای منسوخ‌شده، پرچم `deprecated=True` در دکوراتورهای FastAPI ثبت می‌شود.


* خروجی مستندات خودکار سرور در مسیر `/openapi.json` بلافاصله وضعیت منسوخ بودن متد را به ابزارهای کلاینت منعکس می‌کند.



---

## ۵. رفتار پس از انقضا و بازنشستگی (HTTP 410 Gone)

به محض فرارسیدن تاریخ ثبت‌شده در هدر `Sunset`، سرویس‌دهی روی اندپوینت متوقف می‌شود.
درخواست‌های ارسالی پس از این تاریخ نباید خطای `404 Not Found` دریافت کنند، بلکه سرور یک خطای قطعی **`HTTP 410 Gone`** همراه با راهنمای مهاجرت بازمی‌گرداند:

```json
{
  "error": "Gone",
  "message": "This API endpoint has been permanently retired. Please migrate to the successor version.",
  "retiredAt": "2026-12-31T00:00:00Z",
  "successor": "/api/v2/categories",
  "documentation": "https://api.hesabi.com/docs/migration"
}

```

# ADR-001: Migration from Flask to FastAPI as the Primary Web Framework

## Status
Accepted

## Context & Needs
پروژه حسابی از یک ابزار تک‌کاربره محلی به یک سیستم مدیریت مالی متمرکز و چندکاربره (پشتیبانی از بودجه‌های خانوار) تکامل یافته است. برای ارائه سرویس پایدار به کلاینت‌های متنوع (وب/PWA، ربات تلگرام و اپلیکیشن موبایل)، نیازمند یک Centralized Web API به عنوان منبع واحد حقیقت (Single Source of Truth) هستیم.

برای لایه بک‌اِند، ماندن در اکوسیستم پایتون به دلیل تسلط تیم و سرعت بالای توسعه حفظ شد، اما از میان گزینه‌های موجود:

*فریم Flask (وضعیت موجود): به دلیل معماری Synchronous/Blocking برای بارهای هم‌زمان و توسعه مقیاس‌پذیر نامناسب بود.
* فریم Django: برای یک سرویس API محض، سربار (Overhead) زیادی داشت.
* فریم FastAPI: به عنوان گزینه مدرن و مبتنی بر ASGI بررسی شد.

## Decision
مهاجرت کامل لایه وب پروژه از Flask به FastAPI جهت دستیابی به معماری Async نیتیو و حذف کدهای تکراری اعتبارسنجی (Data Validation).

## Comparison & Trade-off Analysis

### ابزار انتخابی: FastAPI

* نقاط قوت (Strengths):

  * معماری ASGI / Async: پردازش بهینه درخواست‌های هم‌زمان (Concurrent I/O) با آزاد نگه‌داشتن Event Loop.
  * یکپارچگی با Pydantic: اعتبارسنجی و تبدیل خودکار داده‌ها (Serialization) که نیاز به نوشتن دستی try/exceptها و Parse کردن متغیرها در هر روت را حذف و Type Safety را تضمین می‌کند.
  * استاندارد OpenAPI نیتیو: تولید خودکار مستندات تعاملی (/docs) که تست و یکپارچه‌سازی با کلاینت‌ها را تسهیل می‌کند.

* نقاط ضعف و هزینه‌ها (Weaknesses & Costs):

  * سربار یادگیری (Learning Curve): نیاز تیم به درک عمیق‌تر لایف‌سایکل درخواست‌ها در دنیای Async.
  * پیچیدگی دیباگ: سخت‌تر بودن ریشه‌یابی خطاهای ناشی از Race Condition یا فراخوانی‌های Blocking ناخواسته.

### ابزار جایگزین: Flask

* نقاط قوت (Strengths):

  * سادگی فوق‌العاده و مناسب برای ساخت سریع MVP‌های محلی و تک‌کاربره بدون نیاز به کانفیگ اولیه.

* نقاط ضعف در این پروژه (Why it failed for us):

  * معماری WSGI / Blocking: عدم پاسخگویی مناسب به درخواست‌های هم‌زمان بدون مصرف بالای منابع سرور (Thread/Worker Scaling).
  * پراکندگی معماری: نیاز به اضافه کردن چندین کتابخانه شخص ثالث برای اعتبارسنجی داده‌ها و مستندسازی API.


## Decision Rationale
* چرا نقاط قوت FastAPI به هزینه‌هایش چربید؟

  * تضمین ظرفیت آینده (Future-proofing): با رشد احتمالی کاربران فعال (۳ تا ۱۰ هزار کاربر)، لایه Async و مدیریت منابع ASGI مانع از افت پرفورمنس یا نیاز به بازنویسی مجدد سیستم در زیر بار خواهد شد.
  * ارزش افزوده دانش فنی: هزینه یادگیری FastAPI به عنوان سرمایه‌گذاری برای ارتقای استک فنی پروژه و پیاده‌سازی استانداردهای روز صنعت پذیرفته شد.

* تحت چه شرایطی Flask را انتخاب می‌کردیم؟

  * اگر هدف پروژه صرفاً یک ابزار شخصی آفلاین (Self-hosted) بدون نیاز به مقیاس‌پذیری، هم‌زمانی و پشتیبانی از چند کاربر بود، Flask به دلیل سادگی اولیه گزینه منطقی‌تری به شمار می‌رفت.
